# Deploy the IT Helpdesk Agent

*Chapter 1 of 5 — [the IT helpdesk series](#about-this-series).*

AcmeCorp's IT team is drowning in L1 tickets: password resets, software access
requests, "is email down again?". You've been handed an agent that can handle
those, and your job is to get it running somewhere real and talk to it.

By the end of this chapter you'll have a running agent, a first conversation with
it, and a trace showing exactly what it did to answer.

## What You'll Need

- Agent Manager installed and reachable — [on k3d](../guides/on-k3d.mdx) is the fastest route.
- An OpenAI API key. In this chapter the agent calls OpenAI directly; [Chapter 2](./govern-the-model.mdx) puts a gateway in front of it.

The agent itself is the [`it-helpdesk-agent-v2` sample](https://github.com/wso2/agent-manager/tree/main/samples/it-helpdesk-agent-v2).
You don't need to clone or modify it — Agent Manager builds it straight from the
repository. It's a LangGraph agent on FastAPI with nine tools over mock data:
employee lookup, identity verification, tickets, password resets, software
access, system status, policy search, and escalation to L2.

## Step 1: Put It in a Project

Agents live inside [projects](../concepts/project.mdx), and a project is what a
[deployment pipeline](../concepts/deployment-pipeline.mdx) attaches to. So this
isn't just a folder — it decides the promotion path everything inside it will
follow later, in [Chapter 5](./roll-out-agent-version.mdx).

1. Open the Agent Manager Console.
2. Click the **project switcher** in the top navigation.
3. Click **+ Create a Project**, name it `it-support`, and click **Create**.

{/* SCREENSHOT: Project switcher open, with the Create a Project dialog filled in as "it-support" */}

Group agents that work together in one project. A helpdesk agent and a future
ticket-triage agent belong together; an unrelated sales agent does not.

## Step 2: Create the Agent

Inside the project, click **+ Add Agent**, then **Platform-Hosted Agent** —
Agent Manager will build and run this one for you. (The other option,
Externally-Hosted, is for agents already running elsewhere; see
[Internal and External Agent](../concepts/internal-and-external-agent.mdx).)

Choose **Source Code** as the source type and fill in:

| Field | Value |
|---|---|
| **Name** | `it-helpdesk` |
| **GitHub Repository** | `https://github.com/wso2/agent-manager` |
| **Branch** | `main` |
| **Project Path** | `/samples/it-helpdesk-agent-v2` |

{/* SCREENSHOT: Add Agent form, Source Code selected, repository fields filled in with the values above */}

The repository is public, so no Git Secret is needed.

### Build Details

Choose **Python**, leave the start command as `python main.py`, and pick a
language version of `3.11` or later.

Leave **Enable auto instrumentation** checked. This is what makes Step 5 work:
Agent Manager injects an OpenTelemetry init container at build time, so the agent
emits traces without a single line of tracing code in the sample. The full
mechanism is in [Observability](../concepts/observability.mdx).

### Agent Type

Choose **Chat Agent**. That contract is `POST /chat` on port `8000`, taking
`{message, session_id, context}` and returning `{response}` — which is exactly
what the sample's `app.py` serves. Picking **Custom API Agent** here would make
the console expect an OpenAPI spec instead.

### Environment Variables

The sample needs one variable to start. Add it, and mark it **Secret**:

| Key | Value | Secret |
|---|---|---|
| `OPENAI_API_KEY` | your OpenAI key | ✅ |

{/* SCREENSHOT: Environment Variables section with OPENAI_API_KEY added and the Secret toggle on */}

Two optional ones are worth setting now, because later chapters use them:

| Key | Value | Why |
|---|---|---|
| `COMPANY_NAME` | `AcmeCorp` | Appears in the agent's system prompt |
| `AGENT_VERSION` | `1.0.0` | Echoed in every response — this is how [Chapter 5](./roll-out-agent-version.mdx) makes a promotion visible |

Everything else has a default. The variables you *won't* set by hand are
`LLM_PROVIDER_URL`, `LLM_PROVIDER_KEY`, `GITHUB_URL`, and `GITHUB_API_KEY` —
Agent Manager injects those itself in Chapters 2 and 3.

Click **Deploy**.

## Step 3: Watch It Build

Building and deploying are [separate, separately-permissioned
actions](../concepts/agent-lifecycle.mdx#life-cycle-actions), and you'll see them
run in sequence. The build clones the repo, resolves `requirements.txt`, and
produces an image; the deploy places that image in your development environment.

{/* SCREENSHOT: Agent overview during a build, showing build progress and the build logs panel */}

First builds take a few minutes. If it fails, open the build logs from the same
panel — a missing dependency or a bad start command shows up there.

When it finishes, the agent's status becomes `active`. If it sits at
`in-progress` for a while that's normal: the deployment is applied but the
container hasn't passed its readiness probe yet, and Agent Manager deliberately
won't report `active` until it can actually serve traffic.

## Step 4: Talk to It

Open the **Try It** console from the agent's page and send a message:

```text
Hi, I forgot my password and need it reset.
```

The agent should ask you to verify your identity rather than resetting anything.
Give it a real test employee:

```text
My email is alice.chen@acmecorp.com and my employee ID is E-1001.
```

{/* SCREENSHOT: Try It console showing the two-turn conversation above */}

Now try an admin account in a new conversation — `david.kim@acmecorp.com`,
`E-1004`. The agent should refuse the reset and escalate to L2 instead.

That refusal isn't a hardcoded branch. It's the system prompt plus the
`is_admin` flag on the employee record, and in
[Chapter 4](./observe-first-agent.mdx) you'll write an evaluator that checks the
agent actually obeys it every time.

:::tip
The **Try It** console keeps one `session_id` per conversation, which is why the
agent remembers your email on the second turn. Start a new conversation to reset
that memory.
:::

## Step 5: Read the First Trace

In the left sidebar under **Observability**, click **Traces**, and open the trace
for your password-reset conversation.

{/* SCREENSHOT: Trace detail view, root span expanded, showing LLM and tool spans nested beneath */}

Read it top to bottom:

- The **root span** is the whole request — end-to-end latency and the agent name.
- **LLM spans** show the model, the token counts, and how long the call took.
- **Tool spans** show which tool ran, with its input and output.

You should see `lookup_employee` and `verify_identity` fire before any password
tool does. That ordering *is* the identity-first rule being followed, and it's
the exact thing Chapter 4 turns into an automated check.

You wrote no tracing code to get this. The auto-instrumentation you left enabled
in Step 2 did it.

## What You've Built

A platform-hosted agent, built from source, deployed to an environment, holding a
multi-turn conversation, and fully traced.

Note what you did *not* do: no Dockerfile, no CI pipeline, no registry, no
Kubernetes manifests, no OpenTelemetry setup.

## What's Next

limits and no content policy. Security will not love this.
